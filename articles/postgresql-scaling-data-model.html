Throughput degraded near ~100M rows: resolved by changing the data model, not by replacing PostgreSQL

Note: Table and index names are anonymized.

Symptom

During load testing, degradation appeared earlier than projected. As data volume grew, creating a business object involving a bulk insert of approximately 110k rows moved from an acceptable range to tens of seconds. API latency increased, SLA for the create endpoint was no longer met, and under concurrent database load (prolonged IO, WAL, background work) 5xx responses were observed.

The superficial explanation is “PostgreSQL is slow.” The underlying cause was different: the bottleneck lay in storage and indexing design, not in the engine itself as a generic limitation.

Observations in PostgreSQL

When throughput degraded, pg_stat_activity showed a consistent pattern: the session spent time on disk I/O rather than waiting on locks. Typical indicators:

  • wait_event_type = IO, often DataFileRead
  • EXPLAIN (ANALYZE, BUFFERS) with increasing Buffers: ... read=... as data volume grew

In other words, the system read index and heap pages from storage because the working set no longer fit comfortably in the buffer cache. This was not evidence of an incorrect query in isolation; it reflected working-set size relative to available memory.

Root cause (scaling with data volume)

The original design consolidated all historical links in one structure. Each bulk insert incurred three overlapping cost factors:

  1. A surrogate primary key on a random UUID - additional index maintenance per row.
  2. A separate uniqueness path for the natural key (period_id, agreement_id) - another large B-tree to probe and update.
  3. A single global index over full history - each batch incurred cost proportional to current index size, not only to batch size.

ON CONFLICT DO NOTHING is logically simple but not cost-free at scale. In our case, insert cost tracked index size.

Principal conclusion: the constraint was index structure and growth, not an inability of PostgreSQL to perform high-throughput inserts.

Changes (requirements and storage architecture)

Two aspects applied together.

Business requirements: a period cannot exist without agreements. A surrogate row identifier was no longer aligned with the domain model.

Storage changes:

  • discontinue reliance on the surrogate key as the primary identifier;
  • define the primary key as (period_id, agreement_id) so uniqueness and identity match the domain;
  • partition the table so current load operates against smaller physical indexes rather than one unbounded global tree.

Application logic remained the same (uniqueness checks, bulk insert), but the hot path touches a bounded portion of the index instead of a monolith over full history.

Verification (stepwise experiments)

We used a measured approach: stepwise data growth and repetition of the same insert scenario at each stage.

Checkpoints: 0 rows, then 50M / 100M / 150M / 200M (and higher volumes in stress runs).

At each stage we recorded row counts (count(*)), table and index sizes (pg_total_relation_size, per-index sizes), and a reference ~110k-row insert inside BEGIN / ROLLBACK:

begin;

explain (analyze, buffers)
with p as (
  insert into periods
    (created_at, created_by, reason, scope_key, agreements_count)
  values
    (current_date, 'perf_test', 'probe', 'probe', 110437)
  returning id
)
insert into period_agreements
  (period_id, agreement_id)
select
  (select id from p),
  gen_random_uuid()
from generate_series(1, 110437)
on conflict do nothing;

rollback;

We also examined pg_stat_activity during API traffic to align wait events with user-visible latency.

Measurement methodology: EXPLAIN ANALYZE adds overhead and may observe a colder cache than steady production; repeated API calls benefit from warm cache. We used the benchmark as a comparable indicator across dataset sizes, not as a guarantee of production wall-clock time. Results were cross-checked with observed waits (DataFileRead) and end-to-end application latency.

Before (large monolithic indexes, surrogate key path):

  • bulk insert duration in the tens of seconds at scale; in our runs roughly ~20-80s depending on cache state and contention;
  • near ~80-120M rows, SLA pressure matched laboratory observations;
  • in worst cases, EXPLAIN showed large buffer reads on the order of tens of thousands of 8KB pages, i.e. hundreds of MB read from disk per execution with a cold cache.

After (composite PK, partitioning):

  • the same ~110k-row probe stabilized near ~1.0-1.3s on large stages;
  • Buffers read fell to a small, stable band (on the order of ~10-20 pages in our records), indicating the hot path was largely served from memory;
  • in an extended stress run, approximately ~2.5 billion rows were loaded with stable insert latency; the run stopped because free disk space was exhausted, not because the DBMS ran out of CPU or hit a newly discovered algorithmic limit.

Approximately ~20× on that benchmark; more important than the ratio is that performance ceased to track the age of the full table.

Beyond symptom removal, we required a planning horizon that product and operations could use.

Original design: growth on the order of ~200k rows per day (approximately 200k × 365 ≈ 73 million rows per year on top of existing volume) and a laboratory degradation band near ~80-120M rows (tens of seconds per bulk insert, SLA risk) implies, order of magnitude, entry into that band in roughly one year when starting from tens of millions of rows. Without structural change, that maps to recurring incidents (timeouts, degraded endpoint availability, increased operational load).

New design: with composite PK and partitioning, the same insert pattern remained ~1s-class into billions of rows. The risk removed was not “purchase hardware next quarter” but insert cost scaling with total historical index size. For this failure mode, the system is viable on a multi-year horizon subject to retention policy, partition maintenance, and capacity planning.

Stress test limit: the longest run ended when free space on the volume was exhausted. PostgreSQL retained CPU headroom; no new algorithmic ceiling was observed. The desired relationship of limits is: disk quota is reached before the database exhausts its ability to accept inserts.

Practical takeaways

  • “The database is slow” often reflects index growth across full history, not a shortcoming of PostgreSQL as a product.
  • Wait events and buffer reads help distinguish I/O-bound behavior from other causes.
  • If each insert expands a single global index, hardware expansion without model change is typically a tactical mitigation, not root-cause resolution.

Conclusion

The issue was identified during load testing, which reduces risk to production compared with discovery only after deployment.

PostgreSQL was not the defect.
The core issue was insert cost coupled to the size of historical indexes. After breaking that coupling through domain-aligned keys and partitioning, the same workload remained performant at large data volume. Key planning figures: approximately one year to critical degradation under the old schema versus multi-year runway under the new for this class of constraint; in the lab, disk space was exhausted before database throughput became the limiting factor.
