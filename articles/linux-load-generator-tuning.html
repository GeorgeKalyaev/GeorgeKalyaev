Tuning Linux for a Load Generator: limits, sysctl, and verification

Audience: performance testers, SRE, and DevOps engineers running Gatling, JMeter, k6, or similar tools at high concurrency.

Purpose: with many concurrent connections, the bottleneck is often the OS (file descriptors, ephemeral ports, TCP queues, buffers), not only the system under test. This article lists what to change, how to apply settings, and how to verify them.

Baseline environment

Reference VM profile from a typical deployment guide: 16 GB RAM, 8 CPUs, Ubuntu Server LTS.

OS tuning does not replace JVM tuning, test scripts, or connection pooling, but it removes common limits on the load generator host.

Step 1. Open file limit (limits.conf)

On Linux, a TCP connection consumes a file descriptor. Default limits (often around 1000) are usually too low for a load generator: under peak load you may see Too many open files and distorted test results.

Edit /etc/security/limits.conf (for example sudo nano /etc/security/limits.conf). Before the # End of file line, add:

*               soft    nofile          65535
*               hard    nofile          65535

Fields:

  • *: all users (replace with the account that runs the load test if required).
  • soft: default soft limit for descriptors.
  • hard: hard ceiling; cannot exceed this value.
  • nofile: max open files, including sockets.

In nano: save with Ctrl+O, exit with Ctrl+X.

Step 2. Network and TCP parameters (sysctl.conf)

Add to /etc/sysctl.conf or, preferably for maintenance, to /etc/sysctl.d/99-loadgen.conf:

net.ipv4.tcp_max_syn_backlog = 40000
net.core.somaxconn = 40000
net.core.wmem_default = 8388608
net.core.rmem_default = 8388608
net.ipv4.tcp_sack = 1
net.ipv4.tcp_window_scaling = 1
net.ipv4.tcp_fin_timeout = 15
net.ipv4.tcp_keepalive_intvl = 30
net.ipv4.tcp_tw_reuse = 1
net.ipv4.tcp_moderate_rcvbuf = 1
net.core.rmem_max = 134217728
net.core.wmem_max = 134217728
net.ipv4.tcp_mem = 134217728 134217728 134217728
net.ipv4.tcp_rmem = 4096 277750 134217728
net.ipv4.tcp_wmem = 4096 277750 134217728
net.core.netdev_max_backlog = 300000

Parameter roles:

  • tcp_max_syn_backlog: half-open SYN queue on the interface.
  • somaxconn: backlog of connections waiting for accept on listening sockets.
  • wmem_default / rmem_default: default send and receive buffer sizes (8 MB here).
  • tcp_sack: TCP selective acknowledgments.
  • tcp_window_scaling: TCP window scaling for high bandwidth-delay product paths.
  • tcp_fin_timeout: shorter hold time when many connections close.
  • tcp_keepalive_intvl: interval between keepalive probes.
  • tcp_tw_reuse: reuse of sockets in TIME_WAIT for new outbound connections. Often acceptable on a generator client with short-lived sessions; on application servers, validate against kernel version and security policy.
  • tcp_moderate_rcvbuf: receive buffer autotuning for TCP.
  • rmem_max / wmem_max: buffer ceilings (up to 128 MB here).
  • tcp_mem: three TCP memory thresholds (min, pressure, max). Values are in memory pages, not bytes; align with installed RAM.
  • tcp_rmem / tcp_wmem: min, default, and max TCP receive and send buffer sizes.
  • netdev_max_backlog: ingress packet queue when the stack cannot drain fast enough.

For outbound connections, set the ephemeral port range explicitly:

net.ipv4.ip_local_port_range = 10000 65535

This reduces the risk of local port exhaustion when many connections target the same remote IP and port. All generator hosts in an environment should use the same range; otherwise runs are not comparable.

Step 3. Apply settings and re-login

  1. Run sudo sysctl -p.
  2. End the SSH session (exit) and log in again as the same user that will run the load test.

limits.conf is applied on login (PAM). An existing session may keep old limits. sysctl values take effect immediately after sysctl -p.

If the load tool runs as a systemd service, set LimitNOFILE= in the unit file: interactive shell limits and service limits can differ.

Step 4. Verification

After logging in again:

ulimit -a
cat /proc/sys/net/ipv4/ip_local_port_range
grep -v '^#' /etc/sysctl.conf | grep '^net.'

Expected results:

  • open files (-n): 65535 (or your agreed value).
  • ip_local_port_range: the configured range, for example 10000 65535.
  • The third command lists active net.* lines for configuration audit.

Common signs the generator is the limit

  • Connection errors and timeouts on the generator while the target stays lightly loaded.
  • Too many open files in the load driver logs.
  • Cannot assign requested address with a narrow ip_local_port_range and high concurrency to one remote socket.
  • Flat RPS with low utilization on the application under test.

Triage order: limits, ports, network queues, and generator metrics (CPU, RAM, disk), then the SUT profile.

Constraints and risks

  1. tcp_mem, rmem_max, wmem_max: align with real memory and traffic; do not copy values from another VM without recalculation.
  2. tcp_tw_reuse: evaluated differently on application servers than on a generator client.
  3. All generators in one environment should share the same limits, sysctl, and port range; otherwise results are not comparable.

Pre-run checklist

  • limits.conf: nofile soft and hard for the correct user or *.
  • sysctl: full net.* set plus ip_local_port_range if required.
  • sysctl -p executed and SSH session restarted.
  • ulimit -a: open files matches the target.
  • ip_local_port_range identical on every generator host.
  • For systemd: LimitNOFILE checked when the load process is not started from an interactive shell.

Conclusion

Configuring limits.conf and sysctl, re-logging, and checking ulimit and ip_local_port_range gives a reproducible baseline for load tests. After that, tune the scenario, JVM, network path to the target, and the service under test.
